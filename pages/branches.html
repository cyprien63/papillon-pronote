Ce qui protège les deux branches

Sur GitHub, chaque branche porte un jeu de règles qui interdit la suppression, le force-push et la fusion sans PR. Les deux règles sont actives, et le compte Cyprien63 est en contournement explicite : c'est toi qui pushes sur les deux.

Règle Effet
Suppression La branche ne peut pas être effacée par une personne qui n'est pas en contournement
Force-push L'historique ne peut pas être écrasé : personne ne réécrit le passé
Pull request Pas de fusion sans PR, donc chaque intégration est tracée

Une limite à connaître. GitHub n'a pas de règle du type « cette branche ne peut pas aller vers celle-là ». Les règles lisent la branche cible, jamais la source. Concrètement, SITE peut toujours atteindre main par une PR que tu mergerais toi-même au moment où tu le décides — et c'est précisément le but. Ce que les règles empêchent, c'est que ça arrive par megarde, sans que tu t'en aperçoives.

Si tu veux un blocage structurel, il faut que le site vive dans un dépôt séparé : alors main de papillon-pronote ne peut structurellement rien recevoir de SITE.

Ce que la séparation coûte

Rompre l'historique a un prix : les fichiers communs ne sont plus partagés. Aujourd'hui, la branche SITE contient sa propre copie de CLAUDE.md, des skills et des assets graphiques, alors que main garde les siens.

Concrètement, une modification du design dans pronote.css sur main n'atteint pas automatiquement les valeurs du site, et inversement. Les deux copies peuvent diverger.

C'est un compromis assumé : main reste un historique propre de l'extension, et le site peut être déployé sans embarquer le code de l'extension. Le jour où la divergence devient gênante, un sous-module ou un dossier partagé réglerait ça, au prix d'une dépendance entre les deux branches.
